# Design Review: Student Management

Reviewed: `docs/architecture.md` against `docs/requirements.md` (both approved). Independent review; no files other than this one were changed.

## Coverage summary
- FR-1..FR-11 and NFR-1..NFR-5 are all mapped in architecture s8. The traceability is sound. The gaps are in the details below.
- Checked and found fine: Node 26.13.1 accepts `node --test tests/` (verified by running `node --test docs/`); the 500 response is generic; the ID is never taken from the client; `Location` carries only the integer ID; a typed-error mapper exists in one place.

## Findings

| ID | Severity | Section | Issue | Recommendation |
|---|---|---|---|---|
| DR-1 | major | s4 error table, s2 routes | **Missing-ID conflicts with AC-10.** AC-10 requires an invalid-ID error for a *missing* ID on view/update/delete. The architecture only says `PUT /students/` (trailing slash) is `INVALID_ID`. `PUT /students` and `DELETE /students` would fall into "known path, unsupported method" and return 405. Trailing-slash handling is also unspecified for `GET`/`POST /students/`, `/students/1/`, `/students/1/x`, and query strings. | Define one routing rule. Example: path `^/students(?:/([^/]*))?/?$`. `GET`/`POST` with no ID segment are list/add. `PUT`/`DELETE` with no ID segment or an empty one return 400 `INVALID_ID`. `GET /students/` and `GET /students` are the same. Ignore the query string. Anything deeper is `ROUTE_NOT_FOUND`. Add API tests for `PUT /students`, `DELETE /students` and `PUT /students/`. |
| DR-2 | major | s1, s3 file format | **Behavior on a bad data file is undefined** (only "missing file = empty"). If the file is malformed JSON, the wrong shape, has duplicate ids or emails, or has `nextId <= max(id)`, the app can silently start empty and overwrite real data on the next save. It can also reuse IDs, which breaks FR-2 "never reused". | Load rule: if the file is missing, start empty. If it is present but fails parse or schema checks (object, `nextId` safe positive int, each record passes the validator, ids unique, emails unique), fail startup with a clear log message. Never auto-reset. Set `nextId = max(nextId, maxId + 1)`. Create `data/` with `mkdir({recursive:true})` before the first save. |
| DR-3 | major | s6 (rollback), s1 persistence | **Concurrency and atomicity are only half-specified.** "Single user, no concurrency" does not remove interleaving. With async `fs` writes, two overlapping requests can both pass the duplicate check, or a failed save's "rollback" can wipe another request's change. This breaks FR-9 and NFR-2. | Pick the simplest safe option and write it down: perform check, mutate and persist in one synchronous section (`writeFileSync` + `renameSync`; the data is tiny). Or serialize mutations through a single promise queue. Replace "rollback" with build-then-swap: compute the new state, persist it, and only then replace the in-memory state. Also state that `nextId` is not consumed on a failed save. |
| DR-4 | major | s7 layout (`data/` "git-ignored") | **Claim is false.** Verified: `.gitignore` has no `data/` or `data/students.json` entry (it covers only `.env`, `*.log`, `node_modules/`, `*.db`, and similar). Running the app would create student PII (names, emails) that can be committed and pushed in phase 8. | Add a planning/implementation task to add `data/` to `.gitignore`, and a verification check that `git status` stays clean after running the server. Optionally make the data path configurable via `DATA_FILE`. |
| DR-5 | major | s2 server bootstrap | **No bind address.** `server.listen(port)` binds to all interfaces. The API has no auth by requirement and stores PII, so any machine on the network could read or delete records. | Default `HOST` to `127.0.0.1` (overridable by env) and say so in s2. |
| DR-6 | minor | s3 email rule | **Email rule is ambiguous.** "Single `@`, no spaces, domain contains a dot" admits more than intended. Verified in Node: under the loose reading, `a@.com`, `a@b.` and `a@b..c` pass. "No spaces" should mean no whitespace of any kind (tabs and newlines). There is no local-part limit. AC-7 tests cannot be written deterministically. | Pin one regex in the doc, for example `^[^\s@]+@[^\s@.]+(\.[^\s@.]+)+$`. It must be linear-time (no nested quantifiers). Check `length <= 254` first. Add test cases: `abc`, `a@b`, `a@.com`, `a@b.`, `a@@b.c`, `a b@c.d`, `a@b.c\n`. |
| DR-7 | minor | s4 check order | **Ordering vs ACs.** The order puts body validation (422) before existence (404). AC-9 says that for a non-existent ID, update returns not-found. As written, `PUT /students/999` with a bad body returns 422, not 404. The order also omits 413 and non-JSON content-type handling. | Either move the existence check before field validation for update (a cheap lookup, and it matches AC-9 literally), or state the 422-first behavior explicitly as a decision and test it. Place 413 (during body read) and 415 (DR-10) in the order list. |
| DR-8 | minor | s4 INVALID_ID | **ID parsing method unspecified.** Verified pitfalls: `parseInt("12abc")` is 12, `Number("")` is 0, `Number("1e3")` is 1000, `Number("0x10")` is 16, `Number(" 5 ")` is 5. Rejecting leading zeros is stricter than the requirements ("non-numeric"), which is acceptable but should be a stated choice. | Specify: segment must match `^[1-9]\d*$`, then `Number(seg) <= Number.MAX_SAFE_INTEGER`. Do not use `parseInt` or `Number` for validation. Decode the segment once and reject anything that is not digits (for example `%31`, `1%00`). |
| DR-9 | minor | s4 413, server | **DoS controls are thin.** The 10 KB limit has no mechanism. A `Content-Length` check alone misses chunked bodies. There is no mention of timeouts or of what happens on GET/DELETE bodies. | Count bytes while streaming. On overflow, stop reading, respond 413 with `Connection: close`, and destroy the request. Rely on or set `server.headersTimeout`/`requestTimeout`. Ignore (and do not buffer) bodies on GET/DELETE. |
| DR-10 | minor | s4 "JSON only" | **Content-Type is declared but not enforced.** With no auth, a browser page can send a cross-origin `POST` with `text/plain` (a CORS "simple request"), which would add records without a preflight. Rejecting non-JSON types forces a preflight, which fails because no CORS headers are sent. | Require `application/json` on POST/PUT, otherwise 415 `UNSUPPORTED_MEDIA_TYPE`. Send no CORS headers (state this). |
| DR-11 | minor | s3, s6 (unknown fields ignored) | **Prototype hazard is not addressed.** Verified: `JSON.parse('{"__proto__":{"x":1}}')` yields an own `__proto__` key. `Object.assign({}, body)` sets the prototype of the copy (`x` becomes 1); spread is safe. "Ignore unknown fields" is not enough if an implementer merges the body. | The validator must build a fresh object from exactly `name`, `email`, `course` (explicit picks). Never merge or spread the body into a record. Use a `Map` for storage and the email index, and `Object.hasOwn` if reading by key. Add a test posting `__proto__` and `constructor` keys. |
| DR-12 | minor | s6 messages and logging | **Error leakage details.** `INVALID_JSON` could pass through `SyntaxError.message`, which quotes input fragments. Logs could capture request bodies (PII). `ROUTE_NOT_FOUND` might echo the path. | Use fixed messages for `INVALID_JSON`, `ROUTE_NOT_FOUND` and `PAYLOAD_TOO_LARGE`. Log method, path (no query), status and error code only; never bodies. Say so in s6. |
| DR-13 | minor | s7 testability | **Not testable as drawn.** Tests "start server on port 0", but `server.js` only wires and listens. The AC-11 test for a failed save needs a way to inject a failing write; none exists. | Export `createServer({filePath, host, port})` or `createApp` from `server.js` and call `listen` only under `require.main === module`. Let the repository accept an injectable writer (or a read-only temp path) so tests can force a save failure and assert data is unchanged and the response is 500. |
| DR-14 | minor | s1 atomic write | **Write details missing.** The temp file must be in the same directory as the target (rename is atomic only within one volume). On Windows, `rename` over an existing file can fail with `EPERM`/`EBUSY` if antivirus or another handle holds it. A crash can leave a stray temp file. No fsync is mentioned. | State: temp name `students.json.tmp` in the same directory, `writeFileSync` then `renameSync`, remove the temp file on error, surface a failure as a 500 with the in-memory state unchanged. An fsync is optional for this scope. |
| DR-15 | minor | s2 errors, s4 (NFR-4) | **Minor over-engineering and coupling.** The HTTP `Allow` header on 405 and a separate 405 vs `ROUTE_NOT_FOUND` split go beyond the story. `errors.js` carrying HTTP status couples the domain to HTTP. The rollback mechanism is more complex than build-then-swap (see DR-3). | Keep 405 and 404 as plain responses; the `Allow` header is optional. Prefer errors that carry only a `code`, with a code-to-status map in `routes.js`. Drop rollback in favor of build-then-swap. Overall size (6 files, no deps) is appropriate. |

## Verdict
**CHANGES NEEDED.** There are no critical findings and the overall design is sound and appropriately small. Five major findings (DR-1 to DR-5) need to be resolved in `docs/architecture.md` before planning: missing-ID routing against AC-10, data-file validation and ID reuse, atomic persistence and concurrency, the false `data/` ignore claim, and the bind address. The minor findings (DR-6 to DR-15) can be folded in at the same time, or tracked as implementation notes if the human prefers.

## Amendment 3 review (student status)

Scope: `docs/architecture.md` s12 (and the pointer edits in s3, s4, s8) against `docs/requirements.md` Amendment 2 (FR-19..FR-29, AC-18..AC-29, NFR-7). Claims in s12 were checked against `src/studentRepository.js`, `src/validation.js`, `src/studentService.js`, `src/routes.js` and `public/app.js`. s1-s11 were not re-reviewed. No file other than this one was changed.

### Coverage and verified claims
- FR-19..FR-29 are all traced in s12.8; no requirement gap found. Every AC has a named test in s12.6.
- Verified against code: `repository.update` (line 143) rebuilds the record from `data` alone and would drop `status`, so the s12.4 change is required and correctly described. `snapshot` copies all fields, so `status` persists with no further change. `commit` is synchronous (write, then swap), so `setStatus` inherits NFR-2 and the DR-3/DR-14 guarantees.
- The new `ROUTE_RE` is linear (no nested quantifiers; the only repeat is `[^/]*` followed by a literal `/`). Walked through: `/students//status` -> id `''`, status; `/students//` -> collection (unchanged); `/students/1//` -> no match -> 404; `/students/status` -> single ID `status` (see DR-17); `/students/1/Status` -> 404. The status branch must be tested before the existing `segment === ''` branch (routes.js line 86), as s12.3 says; otherwise `/students//status` would hit the collection branch.
- PATCH is not CORS-safelisted and carries JSON, so cross-origin calls still need a preflight that fails (DR-10 holds). `validateStatusChange` returns only the status string, so a PATCH body cannot mass-assign other fields.

| DR-19 | minor | s12.2 flag design, s12.1 / s12.4 | **`acceptStatus` flag: design is acceptable, but its failure mode is silent.** Confirmed over the alternatives: a second POST validator would duplicate the picks and the single-pass error collection (NFR-3), and the default (ignore status) is the right safe default for `PUT`. ### Confirmed without findings (s12.9 items)
- Item 2 (404 before 422 on PATCH): confirmed; mirrors PUT and AC-9, and `setStatus` is synchronous so there is no interleaving.
- Item 3 (options flag): confirmed with the tests in DR-19.
- Item 5 (same-status PATCH writes): confirmed. A skip would add a second code path to save one small write, and the write is what rewrites a legacy file with `status`. FR-23/AC-21 are met either way. Do not add a no-op shortcut.
- Item 8 (no `Allow` on new 405s) and item 9 (`create` default): acceptable (DR-15, and the service always passes a validated value; see DR-19 for the test).
- Over-engineering check: no new files, no new dependencies, no migration step, no status-dependent logic; `checkStatus` plus two thin wrappers is the minimum. Nothing to remove.

### Amendment 3 verdict
**APPROVE.** No critical or major findings. DR-16 to DR-23 are minor; fold DR-16, DR-17, DR-18, DR-20 and DR-22 into `docs/architecture.md` (doc-only edits) and carry DR-19, DR-21 and DR-23 as planning/implementation notes. Implementation may proceed after the human approval gate.
